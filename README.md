# Metal Weight Calculator

Engineering weight calculators for plates, sections, pipes, bars, cones, spheres,
flanges and dished heads.

The project has a static website and an **optional** API:

- **Website** — static files: `index.html` at the repository root plus the pages
  and assets under `frontend/`. Every calculator ships with a generated local
  engine, so the site displays **and calculates** with no server at all. It is
  hosted on GitHub Pages and works on any mobile network, on unstable links and
  offline after the first visit.
- **API** — `backend/`: the source engineering formulas, material densities,
  validation and rate limiting. Deploy it only when a deployment explicitly
  wants remote calculation or centralized logging; it is never required for the
  calculators to work.

## Text and labels — where to edit

Everything a visitor reads is plain source text: an HTML text node, an SVG
`<text>` element, or a JavaScript string. No image on the site carries interface
text — the only images the pages load are `frontend/icons/logo.png` (header) and
the favicon/PWA icons. Dimensions are drawn as SVG text, never as pictures.

| Text you see | Edit it in |
| --- | --- |
| Home headline, section headings, footer | `index.html` |
| Calculator card names, one-line descriptions, categories | `frontend/assets/data/dashboard-data.js` — generated by `tools/generate_dashboard_data.py`, so edit the curated lists in that script and re-run `python tools/generate_dashboard_data.py` |
| About page | `frontend/about/index.html` |
| A calculator's `<title>`, `<h1>`, input labels and placeholders, result labels, "Weight Calculation Formula", the worked example, FAQ, related links | `frontend/calculators/<slug>/index.html` — search for the text you can see |
| Drawing captions `FRONT VIEW`, `SIDE VIEW`, `SECTION VIEW`, `TOP VIEW` | the inline `<svg>` of that page: one `<text>` element per caption, carrying its own `x`, `y`, `fill` and `font-size` |
| Dimension symbols `D L W T E S K P` | the `<text id="dim…">` element in the same SVG — its text content *is* the symbol |
| Dimension values (`L = 100`) | generated at runtime in `frontend/shared/dimension-values.js`, which keeps the symbol text and appends `" = " + value` |
| Drawings built by script (`nut-bolt`, `flange-plate`, `dish-ends`) | that calculator's `.js` — their label, caption and annotation strings are all there |
| Unit note ("All dimensions are in millimeters.") | the calculator `.js` sets it on load and on unit switch, and the page `index.html` holds the same sentence as the no-JS default — change both |
| Validation and error messages | the calculator `.js` |
| Formula text and the worked example | page `index.html`; the maths itself lives in `backend/calculations/` |
| History, keypad, feedback, install pop-up | the matching `frontend/shared/*.js` |

Wording that repeats on every calculator — "Weight Calculation Formula",
"Frequently Asked Questions", "Related Calculators" and so on — is deliberately
kept in each page, so it stays in the HTML for crawlers and for visitors without
JavaScript. Change it everywhere at once with an editor-wide search and replace
(or `grep -rl` plus `sed`) across `frontend/calculators/*/index.html`.

## Languages

There is one English website. The language menu translates the current page in
place and never opens a language folder or changes the URL.

- English text in the pages is the source. Edit it there, as the table above says.
- `frontend/i18n/<code>.json` holds one dictionary per language (`terms`,
  `strings`, `templates`). Edit those files to change a translation.
- `python tools/build_i18n.py` regenerates a tiny `frontend/i18n/translations.js`
  registry, one `frontend/i18n/dict-<code>.js` file per language, and refreshes
  the language menu on all pages. English visitors download no dictionary at
  all; switching language downloads only that one file and caches it offline.
  Bump `RUNTIME_VERSION` in the script (and `CACHE_NAME` in `service-worker.js`)
  whenever generated pages or dictionaries change.
- `frontend/i18n/i18n.js` translates complete interface strings only. Formulas,
  dimensions, units, standard names and numbers do not match the dictionary, so
  they stay unchanged; calculator values and selected options are never touched.
- Numeric conventions live in `frontend/i18n/number-format.js`: Devanagari digits
  for Marathi/Hindi, fullwidth digits for Japanese, Arabic-Indic digits and the
  Arabic decimal separator for Arabic, and locale decimal/group separators for
  German, Spanish, French and Portuguese. The same parser accepts localized or
  plain ASCII input and converts it to a JavaScript number before any formula
  runs, so KG/LB and MM/INCH are unaffected.
- Desktop fields keep the native keyboard but display localized digits and set
  `lang`/`dir` for the selected language. Touch devices use the first-party
  keypad in `frontend/shared/numeric-keypad.js`; its digit keys, decimal key and
  labels follow the active language. Numeric fields stay LTR so the caret and
  decimal order remain correct on RTL Arabic pages. The operating system still
  decides which native keyboard layout is offered; the website never claims to
  change the OS keyboard language itself.
- `python tools/generate_seo.py` refreshes the English canonical/metadata block
  and the 26-URL sitemap after pages change.

## Analytics

The website records calculator views, calculator clicks, Row advertisement
impressions and advertisement clicks. `frontend/analytics/index.html` is the
master dashboard: it combines every Row into summary cards, Row comparison,
charts, campaign performance and date-wise totals, with Today / Yesterday /
Last 7 days / Last 30 days / This month / Custom ranges. Each Row keeps its own
dashboard at `frontend/analytics/a-row/` … `f-row/`, reachable from the master
table. Calculator identity is canonical: a translated page reports the same
calculator and Row as its English reference.

Collection and reports need the optional API in `backend/` (the website stays
static); point `frontend/assets/js/api-config.js` at it. Cost, reach and
external engagement are shown **only** from verified records in
`backend/analytics/campaigns.json` — never estimated from website traffic.

Rows and calculator membership come from
`Material Weight Calculator on Language Ads/row-ads.config.js`; after changing
them run `python tools/build_analytics.py`, which regenerates the dashboards,
the server manifest and the tracker tags on every page. Full setup, endpoints
and privacy notes: [docs/ANALYTICS.md](docs/ANALYTICS.md).

## Hosting

- **Website:** GitHub Pages serves the root `index.html` as the home page — see
  [DEPLOY.md](DEPLOY.md). No API or server-side code is needed for the site to
  display and calculate.
- **API (optional):** deploy `backend/` only if a deployment wants a remote
  source of truth or centralized logging. A static host answers `404` to
  `/api/*`, which is fine: calculators never call it by default.

Remote mode is opt-in, before `calc-api.js` loads:

```js
// frontend/assets/js/api-config.js
window.MW_API_BASE = "https://api.example.com";
window.MW_API_MODE = "remote";   // or window.MW_API_FORCE_REMOTE = true
```

With no switch set, `MWCalc.remoteMode()` is `false` and every calculation is
answered locally. No API key or secret is stored in frontend files; when the API
is used, it allows the site's origin through `ALLOWED_ORIGINS`.

## How calculations work

1. The page reads and validates the user's inputs exactly as before (messages
   and rules live in the page).
2. By default, `frontend/assets/js/calc-engine.js` — generated from the same
   backend modules — computes the finished numbers in the browser. There is no
   request, no spinner and no dependence on DNS, CORS, SSL or signal strength.
3. The page renders those numbers with its existing formatting, drawings,
   history entries, print and PDF code. History is stored on the device.
4. Only when remote mode is explicitly enabled does `calc-api.js` `POST` to
   `<API base>/api/calculate/<calculator>`. A short deadline and the same local
   engine keep the result available if that host is slow or unreachable.

Material densities ship with the site (the same tables as the API), so a
standard material such as Carbon Steel always resolves offline. Remote
deployments may call `MWCalc.loadMaterials(true)` to refresh from `/api/materials`.

The engineering formulas — areas, volumes, surface areas, blank diameters, hole
removal, weights and tonnes — live in `backend/calculations` and are mirrored
into `frontend/assets/js/calc-engine.js` by the generator. Change the backend
modules, then regenerate the engine; never hand-edit the generated file.

### API (optional)

These endpoints are unchanged and are used only in remote mode or by tooling.

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/health` | Service check |
| `GET` | `/api/calculators` | Slugs the API serves |
| `GET` | `/api/materials` | Density tables as JSON |
| `GET` | `/api/bootstrap.js` | Densities as a script (tooling and tests) |
| `POST` | `/api/calculate/:calculator` | Runs one calculation |

Example:

```bash
curl -X POST https://api.example.com/api/calculate/plate \
  -H "Content-Type: application/json" \
  -d '{"values":{"width":1000,"thickness":5,"length":2000},"unit":"mm","density":7.85,"quantity":3}'
```

```json
{"ok":true,"calculator":"plate","units":{"dimensions":"mm","density":"g/cm3"},
 "result":{"areaMM2":5000,"volumeMM3":10000000,"volumeM3":0.01,
           "singleWeight":78.5,"totalWeight":235.5,"totalTonnes":0.2355,
           "materialName":"Custom Material"}}
```

Errors are always JSON: `400` invalid input (with the field name), `401` missing
API key when one is configured, `403` origin not allowed, `404` unknown
calculator, `405` wrong method, `413` body too large, `429` rate limited, `500`
unexpected.

`dish-ends` takes an extra `type` (`flat`, `torispherical`, `ellipsoidal`,
`hemispherical`, `template`) and a density in **kg/m³**; every other calculator
uses **g/cm³**.

## Security

- The API process serves `/api/*` only. The website is static; its generated
  local engine mirrors the backend maths so calculations need no network.
- Inputs are validated and range-checked on the server when the API is used, and
  by the same validation rules in the browser for every calculation.
- CORS allows listed origins (`ALLOWED_ORIGINS`); anything else gets `403`.
- `/api/calculate` is rate limited per client IP (`RATE_LIMIT_MAX` per
  `RATE_LIMIT_WINDOW_MS`).
- Request bodies are capped (`MAX_BODY_BYTES`) and only JSON is accepted.
- Configuration comes from the environment (`backend/.env`, git-ignored).

## Tests

```bash
cd backend
npm test
```

The parity test runs every calculator twice with identical inputs — once with the
pre-restructure page (kept in `backend/test/fixtures/original` as reference
material only) and once with the migrated page calling the API — and compares
every rendered string, the calculation history payload and the result object.
The five dish head types are compared field by field, including the template
station table. It starts its own temporary API server, so no setup is needed.

Expected result: `calculator/scenario pairs compared: 71` followed by `PASS`.

After changing a formula, also run `python tools/build_calc_engine.py` so the
local browser engine stays byte-for-byte aligned with the backend results.
